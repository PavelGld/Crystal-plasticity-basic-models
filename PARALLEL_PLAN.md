# CP-UMAT: план распараллеливания расчёта в Abaqus

Дата: 2026-09-03. Адресат: агент-исполнитель. Текущее состояние: расчёт работает, `cpus=1`.

---

## 0. TL;DR

Есть **две разные оси**, их постоянно путают:

| Ось | Кто параллелит | Что нужно от нас |
|---|---|---|
| **A. Элементная петля Abaqus** (правильная) | Abaqus вызывает UMAT для разных IP одновременно | сделать UMAT thread-safe |
| **B. OpenMP внутри одного вызова UMAT** (тупиковая) | мы сами внутри `umat_()` | ничего не даст — см. §2 |

Работа = **ось A**. Внутри одного вызова UMAT распараллеливать нечего: там Ньютон по 6 неизвестным и LU 6×6, это единицы микросекунд и целиком в L1; OpenMP-барьер дороже самой работы. Параллелизм модели живёт на уровне 64+ точек интегрирования, и его уже реализует Abaqus.

Порядок: Фаза 1 (MPI, без правок кода, даёт ускорение сегодня) → Фаза 2 (thread-safety, основная работа) → Фаза 3 (полнота STATEV) → Фаза 4 (приёмка и масштабирование).

## 1. Как Abaqus/Standard на самом деле параллелит UMAT

Факты из документации (Abaqus Analysis User's Guide, «Parallel execution in Abaqus/Standard»; User Subroutines Reference Guide, §«Ensuring thread safety», §«Allocatable arrays», §«Obtaining parallel processes information»):

1. **Параллельное выполнение элементных операций включено по умолчанию** и управляется `standard_parallel` (значения `all` / `solver`). Элементные операции — это в том числе вызовы UMAT.
2. Два режима: `mp_mode=threads` (потоки в одном процессе) и `mp_mode=mpi` (несколько процессов, домены `STD_PARTITION_n`). Для прямого разреженного решателя на shared-memory машине используется потоковая параллелизация; при MPI-декомпозиции каждый домен обслуживает отдельный MPI-процесс.
3. **Требование к пользовательским подпрограммам:** потокобезопасность, «это исключает common blocks, data statements и save statements». Для MPI-режима потокобезопасность требуется только в гибридном сценарии (MPI + потоки внутри хоста).
4. Инструменты Abaqus для потокового режима (доступны из C++ через `#include <SMAAspUserSubroutines.h>`):
   - `int get_thread_id()` — ID потока, главный = 0, далее 1..N;
   - `int GETNUMTHREADS()` — число потоков в процессе;
   - `GETRANK`/`GETNUMCPUS` — ранг и число MPI-процессов;
   - `MutexInit(i)` / `MutexLock(i)` / `MutexUnlock(i)`, i = 1..100; инициализировать в `UEXTERNALDB`;
   - thread-local и глобальные динамические массивы: `SMALocalFloatArrayCreate(ID,SIZE,INIT)`, `SMALocalFloatArrayAccess(ID)`, `SMAFloatArrayCreate(...)` — документация прямо называет их «потокобезопасной заменой COMMON BLOCKS и SAVE».
5. `PNEWDT` при параллельном счёте: Abaqus берёт **минимум по всем вызовам** за итерацию — наша логика `PNEWDT=0.25` при `step_failed` работает корректно и в параллели.

**Вывод:** ничего «включать» не надо. Нужно убрать из UMAT разделяемое состояние.

## 2. Почему OpenMP «не подцепляется» и почему это не надо лечить

Причины, по которым `/openmp` в нашем объектнике не работает:

1. **Линкует не MSVC, а ifort/Intel-линкер Abaqus** по команде `link_sl` из `abaqus_v6.env`. Наш `.obj`, собранный с `/openmp`, тянет `vcomp140.lib`/`libiomp5md.lib`, которых нет в строке линковки → неразрешённые символы либо молчаливое отсутствие рантайма. Чтобы завести, пришлось бы править `link_sl` в env-файле, добавляя OpenMP-рантайм — и это ровно тот класс правок, который у нас уже ломал CRT-линковку.
2. **Конфликт с рантаймом Abaqus.** Abaqus сам управляет пулом потоков; вложенный OpenMP даёт oversubscription (N потоков Abaqus × M потоков OMP), от чего расчёт становится медленнее, чем на одном ядре.
3. **Нечего распараллеливать.** Профиль одного вызова: `evaluate_Dp` (24 системы × 3 sweep'а), `assemble_J` (24 диад 6×6), LU 6×6. Это ~10⁴ флопов; на пороге накладных расходов OpenMP (~1–10 мкс на регион). Единственный цикл разумного размера — по 24 системам, но он и так векторизуется компилятором.

**Решение:** OpenMP в UMAT-пути **не используем**. `#pragma omp` остаётся только в standalone `RVE.hpp` (там 1000 зёрен — там он уместен) и должен быть надёжно отрезан от UMAT-сборки: убедиться, что `build_cp_umat.bat` не содержит `/openmp` и что `RVE.hpp` не попадает в `#include`-граф `cp_umat.cpp`.

## 4. Фаза 1 — быстрый выигрыш без правок кода: `mp_mode=mpi`

Логика: в MPI-режиме каждый домен — отдельный **процесс**, у него своя копия всех статиков, поэтому `static CPUMAT` перестаёт быть разделяемым.

```
abaqus job=t125 input=... user=cp_umat\cp_umat.obj cpus=4 mp_mode=mpi standard_parallel=all int
```

Что проверить и на что смотреть:

1. **Совместимость с `UNSYMM`.** У нас несимметричный тангенс. Для MPI-режима на кластерах прямой разреженный решатель не поддерживает несимметричные матрицы; на одной машине это должно работать, но **проверить обязательно** — если Abaqus ругается, попробовать `mp_mode=mpi standard_parallel=solver` (тогда элементные операции последовательные — выигрыша по UMAT не будет) либо остаться на threads и делать Фазу 2.
2. **Файловый вывод.** Наш `cp_umat_dump.txt` из нескольких процессов пишется вразнос — включить в имя файла ранг: `cp_umat_dump_r%d.txt`.
3. **Гибридный режим.** Если Abaqus решит использовать hybrid (MPI + потоки внутри хоста), потокобезопасность снова понадобится. Контролировать через `mp_host_list`/`cpus` и проверять `GETNUMTHREADS()` из п.3.3 — должно быть 1.
4. **Определённость результата:** прогнать `tension_8el_random_n20.inp` при `cpus=1` и `cpus=4 mp_mode=mpi`, сравнить поле S33 по элементам. Расхождение допустимо только на уровне ~1e-6 относительных (разный порядок суммирования в решателе), не более.

**Deliverable:** ответ «работает / не работает MPI-режим» + wall time. Если работает — это рабочее решение на время Фазы 2, и с него можно уже считать 1000-элементные задачи.

## 5. Фаза 2 — сделать UMAT потокобезопасным (основная работа)

### 5.1 Аудит разделяемого состояния (сделать первым, это карта работ)

Пройти по `cp_umat.cpp` и `Grain.hpp` и выписать всё, что переживает вызов:

| Объект | Где | Проблема | План |
|---|---|---|---|
| `static CPUMAT cpumat` | `umat_()` | один `Grain*` на все IP и потоки | §5.2 |
| `static bool ready` + `init_params` | `umat_()` | гонка на первом инкременте: два потока одновременно строят `MaterialParams` | §5.3 |
| `Grain::params` | — | read-only после инициализации | оставить общим (это правильно и экономно) |
| `Grain::H`, `tc`, `shifts`, `Stress_v`, `orient_q`, `R_buf`, все `mutable ... _buf` | `Grain.hpp` | рабочее состояние | становится per-thread через §5.2 |
| `Grain::F`, `strain_gl` | `Grain.hpp` | **не сериализуются в STATEV** → смешиваются между IP | §6 |
| `T_voigt_valid`, `tangent_valid` | `Grain.hpp` | флаги валидности кэша | per-thread, плюс сбрасывать в `load_state` |
| `fopen`-дамп | `cp_umat.cpp` | конкурентная запись | §7 |
| `new MaterialParams()` | `init_params` | утечка (однократная) | не критично, оставить |

### 5.2 Архитектура: один `Grain` на поток, состояние — из STATEV

Три варианта, в порядке предпочтения:

**Вариант 1 (рекомендуемый): `Grain` на поток, индексируемый по `get_thread_id()`.**

```cpp
// cp_umat.cpp
#include <SMAAspUserSubroutines.h>

static const int CP_MAX_THREADS = 256;
static Grain* g_grain_by_thread[CP_MAX_THREADS] = { nullptr };  // POD-массив указателей:
                                                                // нулевая инициализация, без CRT

static Grain* grain_for_this_thread(const MaterialParams* params)
{
    int tid = get_thread_id();
    if (tid < 0 || tid >= CP_MAX_THREADS) tid = 0;   // страховка
    if (!g_grain_by_thread[tid])
        g_grain_by_thread[tid] = new Grain(params, Eigen::Quaterniond::Identity());
    return g_grain_by_thread[tid];
}
```

Почему это безопасно без мьютекса: слот `tid` пишет только сам поток `tid`. Почему одного `Grain` на поток достаточно: **всё** состояние точки интегрирования приходит из `STATEV` через `load_state` в начале вызова и уходит через `save_state` в конце — при условии, что §6 выполнен (сейчас `F` не восстанавливается!).

Требования: `#include <SMAAspUserSubroutines.h>` с путём к include-каталогу Abaqus (`%ABAQUS_DIR%\<ver>\code\include`); проверить, что заголовок компилируется с нашими `/GR- /EHsc-`. Если возникнут проблемы — Вариант 1b.

**Вариант 1b: `__declspec(thread)` вместо Abaqus API** (не требует заголовков Abaqus):

```cpp
static __declspec(thread) Grain* t_grain = nullptr;   // TLS, zero-init, CRT-безопасно
```
Обязательно проверить на реальном многопоточном запуске: TLS в DLL, загружаемой Abaqus, обычно работает, но это надо подтвердить экспериментом, а не верой.

**Вариант 2 (самый безопасный, но медленнее): `Grain` на стеке в каждом вызове.**
```cpp
Grain g(params, q); CPUMAT::load_state(&g, STATEV); ...
```
Проблема: `Grain` содержит `std::vector` и `Eigen::MatrixXd` (H — 24×24) → ~10 аллокаций на каждый вызов UMAT, а вызовов ~10⁵–10⁶ за расчёт. Держать как эталон корректности для сверки с Вариантом 1, не как продакшн.

**Вариант 3 (не делать): `Grain` на каждую IP, индекс `NOEL*8+NPT`.** Память ~ (число элементов × 8 × размер Grain), и упирается в проблему статических массивов Eigen-объектов, уже описанную в README.

### 5.3 Инициализация параметров без гонки

```cpp
// в UEXTERNALDB (LOP=0): MutexInit(1);
static const MaterialParams* g_params = nullptr;
if (!g_params) {
    MutexLock(1);
    if (!g_params) g_params = build_params(PROPS, NPROPS);   // double-checked
    MutexUnlock(1);
}
```
Понадобится добавить `uexternaldb_` (C++, extern "C", имя со подчёркиванием) — там же `MutexInit` для всех используемых мьютексов, как требует документация.

Отдельно зафиксировать в README известное ограничение: `MaterialParams` строится **один раз** из PROPS первого встреченного материала. Для нашей схемы material-per-element это корректно, только пока все материалы отличаются исключительно кватернионом PROPS[10–13]. Если появятся разные упругие константы — нужен кэш параметров по ключу (c11,c12,c44,hard_mode,...) под мьютексом. Добавить проверку: при первом заходе в IP сравнивать PROPS[1..9] с сохранёнными и, при расхождении, писать предупреждение (один раз, из потока 0).

## 6. Фаза 3 — полнота состояния в STATEV (обязательна перед Фазой 2)

Пока `F` и `strain_gl` живут только в объекте `Grain`, любое переиспользование объекта между IP их перемешивает. При `cpus=1` это уже неверно (просто незаметно, т.к. `NLGEOM=NO` и `strain_gl` идёт только в диагностику), а при нескольких потоках станет источником невоспроизводимости.

Действия:

1. Расширить `NSTATV` 70 → 80 и зафиксировать раскладку:
   ```
   0–5    stress_v (crystal frame)
   6–9    quaternion
   10–33  tc[24]
   34–57  shifts[24]
   58–66  F[9]           ← НОВОЕ (row-major)
   67     sim_time
   68     acc_def
   69     guard 123456.0
   70–73  диагностика: кватернион (SDV71–74)
   74     NOEL, 75 NPT, 76 get_thread_id(), 77 счётчик step_failed
   78–79  запас
   ```
   Прежние диагностические слоты 60–65 **освободить** — они пересекутся с `F`. (Напоминание: слоты 56–57, куда агент писал PROPS, перекрывали `shifts[22..23]` — эту запись уже убрали, не возвращать.)
2. `Grain`: добавить `set_F(const Eigen::Matrix3d&)` / `get_F()`, восстанавливать в `load_state`, писать в `save_state`, пересчитывать `strain_gl` после восстановления.
3. `load_state` должен также сбрасывать `tangent_valid = false` и `T_voigt_valid = false` (последнее уже делает `set_orientation`).
4. Обновить `*DEPVAR` во всех `.inp` (70 → 80) и генераторы (`gen_per_material.py`).

**Тест корректности (важный):** прогнать `tension_8el_random_n20.inp` при `cpus=1` до и после Фазы 3. Поля S33 должны совпасть до ~1e-9 (F в small-strain не влияет на напряжение). Если разошлись — где-то `F` всё-таки влияет на отклик, и это надо понять до параллели.

## 7. Фаза 4 — дисциплина ввода-вывода и мьютексов

1. Любая запись в файл из UMAT — либо только из потока 0 (`if (get_thread_id() == 0)`), либо под `MutexLock`. Документация прямо рекомендует первое как более быстрое.

## 8. Фаза 5 — приёмка и масштабирование

Критерии приёмки (все обязательны):

1. **Определённость по числу ядер.** `tension_8el_random_n20.inp` и `tension_125el.inp`: поле S33 при `cpus=1`, `2`, `4`, `8` совпадает в пределах 1e-6 относительных. Сравнение — скриптом по ODB (у вас есть `extract_125el.py`), а не глазами.
2. **Отсутствие гонок при повторе.** Один и тот же `cpus=4` запуск дважды: побитово одинаковое число инкрементов и итераций. Расхождение = гонка.
3. **Масштабирование.** Таблица wall time для 1/2/4/8 ядер на `tension_1000el.inp`. Ожидание для CPFEM: элементные операции ускоряются почти линейно, но общее время ограничено решателем — реалистично 2.5–4× на 4 ядрах. Если ускорения нет вовсе — смотреть §9.1.
4. **Стресс-тест на неоднородность.** 1000 элементов, все ориентации разные (полный `gen_per_material.py`), `cpus=4`: расчёт доходит до конца шага.
5. Оба режима: `mp_mode=threads` и `mp_mode=mpi`.

## 9. Риски и подводные камни

1. **Ускорения нет, хотя код потокобезопасен.** Причины по порядку проверки: (а) `standard_parallel=solver` вместо `all`; (б) задача слишком мала — на 8 элементах параллель бессмысленна, мерить только на 125+; (в) время уходит в решатель, а не в UMAT (проверить долю по логу); (г) лицензионные токены ограничивают `cpus`.
2. **Разбалансировка домена.** У CPFEM стоимость точки зависит от того, сколько подшагов и fallback'ов потребовалось; в Standard пользовательское разбиение доменов недоступно, партиционирование чисто пространственное. Следствие: часть потоков простаивает. Лечится не кодом, а более равномерной физикой (наш кап подшагов из круга 1 как раз срезает патологические выбросы).
3. **`PNEWDT` в параллели** — берётся минимум по всем вызовам; это то, что нам нужно, но означает, что один «плохой» IP режет шаг всей модели. Диагностику `step_failed` (STATEV[77]) стоит выводить в ODB, чтобы видеть, какие элементы виноваты.
4. **Eigen и выравнивание.** Мы уже используем фиксированные размеры; при переходе на per-thread объекты через `new` выравнивание обеспечивает Eigen сам. Не заводить статические/глобальные объекты Eigen (см. README § CRT and Static Arrays).
5. **`.env`-правки.** Любые изменения `compile_cpp`/`link_sl` фиксировать в репозитории вместе с причиной; это главный источник «у меня не собирается» между машинами.
6. **Не откатывать фиксы кругов 1–2** (поворот `T(R)·C·T(Rᵀ)`, цепной тангенс, `.eval()` вместо `noalias()` при самоприсваивании, `DTIME<=0`).

## 10. Чего НЕ делать

- Не добавлять `/openmp` в `build_cp_umat.bat` и не править `link_sl` ради OpenMP-рантайма (§2).
- Не пытаться распараллелить `solve_implicit`/`evaluate_Dp` — там нет работы на параллель.
- Не заводить `Grain` на каждую IP (память + статические Eigen-массивы).
- Не использовать `std::mutex`/`std::thread`/`std::atomic` из стандартной библиотеки в UMAT-пути — тянет CRT, которую мы с таким трудом отрезали; для синхронизации есть `MutexLock` от Abaqus.
- Не переходить на `cpus>1` до выполнения Фазы 3: без `F` в STATEV результат будет зависеть от числа потоков.
