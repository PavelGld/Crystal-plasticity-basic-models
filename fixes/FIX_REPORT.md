## 1. КОРНЕВАЯ ПРИЧИНА: алиасинг Eigen в `CPUMAT::step` (cp_umat.cpp)

```cpp
// было
sv.noalias() = V_to_A() * sv;
// стало
sv = (V_to_A() * sv).eval();
```

`noalias()` при самоприсваивании заставляет Eigen писать результат прямо в `sv`, без временного
объекта. Строка 5 матрицы `V_to_A` (Abaqus-компонента σ23) читает `sv(3)`, который к этому моменту
уже перезаписан строкой 3. В результате **каждый вызов UMAT возвращал Abaqus
`STRESS[σ23] = σ12/2`, а истинное σ23 терялось**.

Доказательство (упругая проба, identity, `tests/dump_fd.cpp e`), матрица FD = d(STRESS)/d(DSTRAN):

| до фикса | после фикса |
|---|---|
| ∂σ23/∂γ12 = 14170 (= c44/2), ∂σ23/∂γ23 = 0 | ∂σ23/∂γ23 = 28340, остальные 0; DDSDDE − FD = 0 точно |

Почему баг был невидим:
- живёт в обёртке UMAT — standalone-тесты Grain/RVE его не видят;
- при identity-растяжении σ12 = σ23 = 0 — все identity-кейсы (1, 8, 125, 1000 элементов) корректны;
- `DDSDDE` считался через те же матрицы **правильно** → Abaqus получал верный тангенс и неверное
  напряжение; глобальный Ньютон не мог загнать невязку в ноль по компонентам 23 →
  линейный «пол» невязки → TOO MANY ATTEMPTS ровно там, где межэлементное сдвиговое равновесие
  существенно (разные ориентации).

Дополнительно проверено: других `x.noalias() = ... * x` в Grain.hpp нет.

## 2. Цепной консистентный тангенс через подшаги (Grain.hpp)

`tangent_buf` после `Simulate_Step` был тангенсом *последнего подшага*, а не производной полного Δσ
по полному Δε. При n_power = 50 в активных направлениях `J⁻¹ ≪ I`, и истинный тангенс ≈ C_last/N —
код завышал его в N раз. Скалярная модель: N=5 → завышение 4.94×.

Реализовано:
- `solve_implicit(double dt, int depth, double weight)`; вес = dt_sub/dt_inc, в fallback-бисекциях `0.5·weight`;
- `tangent_buf` обнуляется в начале `Simulate_Step` (integ_mode==1) и накапливается:
  `tangent_buf = J⁻¹(tangent_buf + weight·P_eff)` (при N=1 — прежняя формула).

FD-ошибка тангенса на полной модели (KM-упрочнение, ротация Тейлора, случайная ориентация):
10–19% → 1–3% (после п.1 → 0.15–0.2%).

## 3. `DS_CRITICAL_IMPL`: 1e-4 → 2e-3 (Grain.hpp)

Типичный инкремент Abaqus (Δε ≈ 5e-4) при пороге 1e-4 дробился на ~5 подшагов, и `ceil(ds/crit)`
скакал между итерациями равновесия (4↔5) — σ(ε) становилась разрывной на величину ошибки
интегрирования, давая «пол» невязки. При 2e-3 такой инкремент = один неявный подшаг.

## 4. Доделан PNEWDT (Grain.hpp + cp_umat.cpp)

- `Grain::step_failed` (сбрасывается в `Simulate_Step`, ставится при `MAX_FALLBACK_DEPTH`),
  геттер `get_step_failed()`;
- `CPUMAT::step`: `if (g->get_step_failed()) PNEWDT = 0.25;` DDSDDE при этом — упругая
  (через `tangent_valid=false`).

## 5. Кап на число подшагов (Grain.hpp, только под ABAQUS_UMAT)

```cpp
if (params->integ_mode == 1 && n_substeps > 200) { step_failed = true; tangent_valid = false; return; }
```

Мусорный глобальный итерат (|Δε| ~ 0.1 и более) давал десятки тысяч подшагов — UMAT «висел»
(в мини-МКЭ воспроизведено: первый инкремент не завершался). Теперь это обычный cutback.

## 6. Мелочи

- `update_H_KM()` в присланном Grain.hpp был **private**, а `load_state` его вызывает — файл не
  компилировался. Сделан public + добавлен `update_H_KM_if_needed()` (только при `hard_mode==2`;
  раньше условие `H.rows()>0` срабатывало и при hard_mode 0/1).
- `test_fd.cpp` / `fe_test.cpp` компилируются с `-DABAQUS_UMAT` — тем же флагом, что и .obj.

## Результаты проверок вне Abaqus

| Проверка | До | После |
|---|---|---|
| Упругий FD тангенс (identity) | ошибка в строке σ23 = c44/2 | 0 точно |
| FD тангенс, полная модель, random q | 15–19% | 0.15–0.2% |
| Мини-МКЭ, 8 identity элементов | 27.2 МПа равномерно (t=0.2) | без изменений |
| Мини-МКЭ, 8 random q (ваши кватернионы) | зависание в инкременте 1 / пол невязки 1e-2 | идёт, 3–6 итераций на инкремент, cutback'и единичные и восстанавливаются (проверено ~10 инкрементов, ограничение по времени песочницы) |

Ожидание в Abaqus: `tension_random.inp` — сходимость без резания шага; `tension_8el_same.inp` —
однородное поле; `tension_8el_random.inp` — сходится, S33 с разбросом по элементам.
Если на первом инкременте всё ещё будет cutback — это нормально (начальный dt=0.005 даёт упругий
предиктор ≫ tc0 при n=50); поднимите `INC` до 1000.

## Как воспроизвести проверки (Linux, g++/Eigen 3.4; под MSVC аналогично)

```bash
# структура: cp_model/{tensor_utils.hpp,MaterialParams.hpp,Grain.hpp}, cp_umat/{cp_umat_types.hpp,cp_umat_interface.hpp,cp_umat.cpp}
g++ -O2 -std=c++17 -DABAQUS_UMAT -I . -I <eigen> tests/dump_fd.cpp cp_umat/cp_umat.cpp -o dump_fd && ./dump_fd e   # должно дать нули
g++ -O2 -std=c++17 -DABAQUS_UMAT -I . -I <eigen> tests/test_fd.cpp cp_umat/cp_umat.cpp -o test_fd && ./test_fd r    # rel err ~2e-3
g++ -O3 -std=c++17 -DABAQUS_UMAT -I . -I <eigen> tests/fe_test.cpp cp_umat/cp_umat.cpp -o fe_test && ./fe_test r 0.1   # 8 random q
#   fe_test i — identity; fe_test s — все элементы с одним не-identity кватернионом
```

Рекомендация: добавить упругую FD-пробу через `CPUMAT::step` со сдвиговыми DSTRAN в doctest —
она ловит именно тот класс багов (обёртка/конвенции), который не видят ни кристальные тесты,
ни identity-кейсы.

## Открытое (не блокирует)

- `static CPUMAT` — по-прежнему не thread-safe, `cpus=1`.
- Кламп `RATIO_MAX=2` при n=50: производная в клампе считается как у неклампированной функции;
  на сошедшемся состоянии кламп неактивен, но робастность локального Ньютона на «диких» trial-состояниях
  можно улучшить (согласованная производная в клампе или гладкий кап).
- Остаточная FD-ошибка тангенса 0.15–0.2%: приближение производной sweep-цикла упрочнения + лаг
  ротации между `R` начала подшага и `R` конца.
