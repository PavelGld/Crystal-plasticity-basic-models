# Ревью: размер инкремента, n=50, время расчёта на Neper-сетке

Дата: 2026-09-14. Ответ на `INCREMENT_AND_N_ISSUE.md`.

## 0. TL;DR

Главная причина «шаг не растёт» — **наш UMAT**, одна строка: `PNEWDT = 1.0` в `CPUMAT::step()`.
Abaqus передаёт в UMAT большое значение PNEWDT и берёт **минимум по всем вызовам** как множитель
нового dt; «1.0» = «оставить как есть». Мы сами запрещали Abaqus увеличивать шаг. Ваш `.sta`
это и показывает: инкременты сходятся за **1 итерацию**, а dt намертво стоит на стартовом
(0.0001 при dtmax=0.001; 0.0001875 в шаге 2). Оценки «11 ч / 50 ч» выведены из этого искусственного
ограничения.

Второе: падение на Δε=0.001 — это старт **нового `*STEP`**, а не тангенс при упрочнении. Тангенс
с упрочнением проверен FD-тестом (ошибка 3–6e-4), O(n)-связка — тождество (1e-13).

## 1. PNEWDT (вопрос №3) — исправлено

`cp_umat.cpp`: из `step()` убрано безусловное `PNEWDT = 1.0` (и в ветке `DTIME<=0`). PNEWDT теперь
меняется только при провале локального интегратора (`= 0.25`). Документация UMAT: *«PNEWDT is set
to a large value before each call to UMAT. … If PNEWDT is given a value that is greater than 1.0 for
all calls … and the increment converges, Abaqus/Standard may increase the time increment. The
suggested new time increment is PNEWDT × DTIME, where PNEWDT is the minimum value for all calls»*.

Что ожидать: с `I_G=4` (ваш `*CONTROLS`) dt растёт ×1.5 после двух инкрементов, сошедшихся за ≤4
итерации, пока не упрётся в dtmax или в инкремент, где итераций станет больше `I_R=10` (тогда ×0.75).
Т.е. Abaqus **сам найдёт максимальный рабочий Δε** для n=50 — не надо подбирать руками.

## 2. Падение при Δε=0.001 (вопросы №1, №4)

`evidence_n50_linesearch.msg`, шаг 2, инкремент 1: невязка 3.5e-2 → 3.3e-2 → 2.7e-2 → 2.65e-2 → 4.3e-2
→ 5.7e-2 → 0.141 при допуске 2.4e-5, line search режет ньютоновский шаг до 0.03–0.15. Это не
«маргинальные 1.5%», а отсутствие сходимости — и она объяснима без всякого бага:

1. **Первый инкремент нового `*STEP` Abaqus считает без экстраполяции** и предварительно вызывает
   UMAT с `DSTRAN = 0` (документация: *«passes zero strain increments … to start the first increment
   of all the steps»*). В законе Хатчинсона γ̇ = γ̇₀·D_eq·(τ/τc)ⁿ при D=0 пластическая скорость
   **нулевая** → тангенс в этом вызове **упругий**. Первая поправка (= весь инкремент, это нормально:
   `LARGEST CORRECTION == LARGEST INCREMENT` на 1-й итерации без экстраполяции — не симптом) толкает
   все 186 000 IP упруго на Δε=0.001 = 10× предыдущего шага при tc0=6 МПа — τ/τc ≫ 1 везде, дальше
   Ньютон из этого состояния при n=50 не вылезает.
2. Внутри шага, с экстраполяцией, Δε=1.5e-3 при n=50 в мини-МКЭ сходился за 4–6 итераций.
   Двухшаговый дек ломает именно это.

**Исправление в генераторе (`neper2abaqus.py`):** один `*STEP` на всю деформацию, стартовый dt
малый, dtmax большой (по умолчанию 10·dt), рост — автоматический (п.1). Никаких «шаг 1 для
транзиента + шаг 2 крупный»: транзиент пройдёт сам за счёт роста dt.

Про принципиальное ограничение: при n=50 поверхность текучести практически многогранная,
переключение активных систем между итератами делает сходимость линейной. Реалистичный рабочий
Δε для n=50 — ~5e-4…1e-3 с экстраполяцией; Abaqus теперь сам выйдет на это плато. Если нужна
быстрее — n=20 (~2× крупнее шаг), но это изменение материала, а не численный трюк.

## 3. Тангенс при упрочнении (вопросы №1, №2) — корректен

- FD-тест в `PERF_REVIEW` **был** с упрочнением: `PROPS[14..18] = 1, 2, 115, 34, 2.25`,
  `hard_mode=2` — те же 19 констант, что в `gen_per_material.py`. Повторно сегодня, n=50, случайная
  ориентация: ошибка `DDSDDE` против `d(STRESS)/d(DSTRAN)` = **3.5e-4 … 6.5e-4**.
- O(n)-связка: для `H = q·1·hᵀ` с `diag(H) = h` (ровно так строит `update_H_KM`)
  `Σ_j H(i,j)γ̇_j = q·Σ_{j≠i} h_jγ̇_j + h_iγ̇_i = q·S + (1−q)·h_iγ̇_i`. Проверено численно на случайных
  h, γ̇, G (n=24, q=2): |полная − быстрая| = 2.8e-14 (dtc), 3.4e-13 (строки G). Член не потерян;
  при q=2 множитель (1−q) = −1 — это алгебра, не ошибка.

## 4. Время расчёта: где оно на самом деле

Ваши 20 с/инкремент при 186k вызовов UMAT: UMAT ≈ 186k × 34 мкс ≈ 6.3 с на итерацию одним
ядром, на 4 потоках ~1.6 с; при 1–2 итерациях это 2–3 с из 20. **Остальное — Abaqus**: UNSYMM
direct sparse на 201k DOF с C3D10 (широкая лента) и вывод. Отсюда рычаги по убыванию:

1. **Рост dt (п.1) + один шаг (п.2).** Ожидание: dt выйдет на 5e-4…1e-3 → 1000–2000 инкрементов
   вместо 5300; при 20 с — 6–11 ч на этой сетке. Это до сокращения сетки.
2. **Сетка (вопрос №5).** 232 элемента C3D10 на зерно — на порядок избыточно для текстуры: зерно
   разрешается 8–30 элементами (C3D8) или ~20–50 C3D10; для ODF важна статистика по зёрнам, а не
   внутризёренные градиенты. Neper: `-rcl 0.6…0.8` (или regularization `-reg 1` + огрубление) даст
   4000–8000 элементов на 200 зёрен вместо 46 499. Решатель дешевеет суперлинейно (~N^1.5 для 3D),
   UMAT — линейно: ожидаемо **10–20×** по времени на инкремент. Целевой порядок: 1000 инкрементов ×
   1–2 с ≈ 30 мин на 4 потоках.
3. **`UNSYMM=YES` — проверить, нужен ли.** Несимметрия нашего тангенса (член c·gᵀ) мала;
   симметричный решатель ~2× дешевле по памяти и времени. Прогнать с `UNSYMM=NO` на маленькой
   сетке: если число итераций не растёт — выключить.
4. **Частота вывода.** `FREQUENCY=50` с `S, E, LE, SDV` (70 SDV × 186k IP) — при 1000+ инкрементов
   это десятки ГБ ODB и заметное время записи. SDV — только нужные (`SDV7–10` кватернион,
   `SDV11–34` tc при необходимости), частоту — по деформации, а не по инкрементам.

## 6. Что НЕ является причиной (чтобы агент не тратил время)

- Консистентный тангенс при упрочнении — проверен (§3).
- O(n) Kocks-Mecking — тождество (§3).
- `LARGEST CORRECTION == LARGEST INCREMENT` на первой итерации — нормальное поведение без
  экстраполяции, не симптом «упругого тангенса».
- Скорость деформации — не трогать, согласен.
