# Проблема: размер инкремента и степень n (n=20 vs n=50)

Дата: 2026-09-14. Контекст: CPFEM UMAT в Abaqus/Standard, Neper-сетка 200 зёрен.

---

## 0. TL;DR

Две отдельные проблемы, которые часто путают:

1. **Баг в генераторе дека (уже исправлен).** Мой `neper2abaqus.py` писал
   **16** констант материала вместо **19**: `n_power=20` вместо `50` и **полностью
   отсутствовало упрочнение** (`h0`, `ts`, `alfa` уходили в 0). То есть все прогоны
   Neper считались с «нечистым» материалом.
2. **Размер инкремента.** Даже с правильным материалом Abaqus не позволяет взять
   крупный шаг: `Δε=0.001` падает (8 отрицательных собственных значений), а
   `Δε=0.0005` держится. Итог: 100% деформации при `Δε=0.0005` — это **2000
   инкрементов ≈ 11 ч** на 46499 элементах.

---

Референсные параметры материала (из `gen_per_material.py`, 19 значений):

| Параметр | Значение | Индекс |

| hard_mode | 2 (Kocks-Mecking) | 4 |

## 2. Баг генератора: 16 констант вместо 19 (ИСПРАВЛЕНО)

`cp_umat_validation/neper2abaqus.py` писал:

```python
f.write("*USER MATERIAL, CONSTANTS=19, UNSYMM\n")
f.write("0, 106750, 60410, 28340, 2, 2, 1, 6\n")
f.write("0.588235, 20, %.10f, %.10f, %.10f, %.10f, 1, 2\n" % (w,x,y,z))   # 8+8 = 16
# ← строки "115, 34, 2.25" не было
```

Должно быть (как в `tension_343el_random.inp`):

```python
f.write("*USER MATERIAL, CONSTANTS=19, UNSYMM\n")
f.write("0, 106750, 60410, 28340, 2, 2, 1, 6\n")
f.write("0.588235, 50, %.10f, %.10f, %.10f, %.10f, 1, 2\n" % (w,x,y,z))
f.write("115, 34, 2.25\n")
```

**Последствия старого дека:**
- `n_power=20` вместо 50 → материал слишком рейт-зависимый;
- `h0=ts=alfa=0` → `update_H_KM()` даёт `H≡0` → **упрочнения нет вообще**;
- `CONSTANTS=19` при 16 значениях — Abaqus добивает нулями (нужно проверить,
  нет ли смещения при чтении).

> ⚠️ Это надо перепроверить: все предыдущие выводы по скорости/сходимости Neper
> относятся к материалу **без упрочнения**. Поведение с `h0=115` будет другим.

## 3. Проблема размера инкремента

### 3.1. Наблюдения по прогонам

| Прогон | Δε старт | max Δε | Что произошло |
|---|---|---|---|
| `neper_v2` | 0.0005 | 0.01 | 0.0005 держится, 645 инкр, `EQUIL=1`, 0 cutback |
| `neper_100` | 0.005 | 0.02 | inc 1 **fail** → 0.00125 **fail** |
| `neper_100` | 0.001 | 0.004 | inc 1 **fail** (4 ит.) → 0.00025 ok (7 ит.) → застрял на 6.25e-5 |
| `neper_100` | 0.0005 | 0.0005 | inc 1 **fail** → 0.000125, не растёт |
| `neper_100` | 0.0001 | 0.001 | inc 1 **ok** (2 ит.), 0.0001 постоянный, **не растёт** |
| two-step | s1=0.0001 / s2=0.001 | — | s1 ok; s2 inc 1 **fail** → 6.25e-5 |

### 3.2. Evidence: падение при Δε=0.00125

`.msg` (прогон `neper_100`, шаг 0.00125):

```
 ***WARNING: THE SYSTEM MATRIX HAS 8 NEGATIVE EIGENVALUES.
 ...
 AVERAGE FORCE                      1.094E-03
 LARGEST RESIDUAL FORCE              2.33       AT NODE      13211  DOF  3
 LARGEST CORRECTION TO DISP.         1.689E-02
          FORCE     EQUILIBRIUM NOT ACHIEVED WITHIN TOLERANCE.
```

Невязка 2.33 против нормы сил 1.1e-3 — расхождение в ~2000 раз. Глобальный
Ньютон не сходится.

### 3.3. Наблюдение: Abaqus НЕ увеличивает инкремент

При идеальной сходимости (`EQUIL=1`, `ATT=1`) и `max Δε > Δε_start` инкремент
**остаётся равным стартовому** и не растёт:

```
   1     8   1     0     2     2  0.0008   0.0008   0.0001000
   1     9   1     0     2     2  0.0009   0.0009   0.0001000
   ...
```

После cutback'а инкремент тоже не восстанавливается (застревает на 6.25e-5).

### 3.4. Следствие: время расчёта

| Параметр | Значение |
|---|---|
| UMAT-вызовов на инкремент | 46499 × 4 ≈ **186 000** |
| DOF | 201 099 (unsymmetric direct sparse) |
| Время на инкремент | **~20 с** (cpus=4) |
| 100% при Δε=0.0005 | 2000 инкр → **~11 ч** |
| 100% при Δε=6.25e-5 | 16000 инкр → **~89 ч** (тупик) |

### 3.5. ПОВТОР с корректным материалом (n=50 + упрочнение)

Дек пересобран (19 PROPS, `n=50`, `h0=115, ts=34, alfa=2.25`), двухшаговый:
шаг 1 (ε 0→0.002, Δε=0.0001), шаг 2 (ε 0.002→1.0, старт Δε=0.001).

**Обнаружено: в деке отсутствовал `*CONTROLS, PARAMETERS=LINE SEARCH`** —
а рабочий `tension_343el_random.inp` его содержит. В Abaqus line search по
умолчанию **выключен**.

| Прогон | Δε | Результат |
|---|---|---|
| без line search | 0.0001 | inc 2 **падал** (`1U`), шаг → 2.5e-5 |
| **с line search** | 0.0001 | inc 1–20 проходят чисто (1–2 итр.), **0 cutback** |
| с line search | 0.001 (старт шага 2) | inc 1 **падает** (8 итр.) → 0.00025 (12 итр.) → **0.0001875** |

Характер падения (с корректным материалом):
- **Нет** отрицательных собственных значений (в отличие от n=20);
- Невязка **1.5%** при допуске **0.5%** — сходимость маргинальная;
- `LARGEST CORRECTION TO DISP == LARGEST INCREMENT OF DISP` — первая
  ньютоновская поправка = 100% инкремента (тангенс почти «упругий» → перелёт).

**Следствие:** с корректным материалом инкремент садится на **0.0001875** →
100% деформации = **~5300 инкрементов ≈ 50 ч** на этой сетке. Непрактично.

### 3.6. Вывод по времени

| Материал | Δε | Инкр. до 100% | Время |
|---|---|---|---|
| n=20, без упрочн. (старый) | 0.0005 | 2000 | ~11 ч |
| **n=50 + упрочн. (верный)** | **0.00019** | **~5300** | **~50 ч** |

> Верный материал сходится заметно тяжелее. Для 100% на этой сетке (232
> эл/зерно) — **нереально**. Нужно либо чинить сходимость, либо резать сетку
> на порядок-два.

## 4. Вопросы к ревьюеру

1. **Тангенс при упрочнении.** С корректным материалом (n=50 + упрочнение)
   первая ньютоновская поправка равна 100% инкремента
   (`LARGEST CORRECTION == LARGEST INCREMENT`), а невязка садится на 1.5% при
   допуске 0.5%. Похоже на слишком «упругий» консистентный тангенс —
   недоучитывается вклад упрочнения. Проверить FD-тестом тангенс **именно с
   `h0=115, ts=34, alfa=2.25`** (в `fixes 3/PERF_REVIEW.md` FD-тест был без
   учёта этих параметров).

2. **O(n) оптимизация Kocks-Mecking.** В `Grain::evaluate_Dp` связка заменена
   на `q·s_all + (1−q)·H(i,i)·γ̇_i`. Вывести/проверить тождество при
   `H = q·1·hᵀ + (1−q)·diag(h)` — нет ли потери члена при упрочнении.

3. **Почему Abaqus не растит инкремент?** При `EQUIL=1` и `max ≥ initial`
   автоматическое увеличение должно работать, но шаг остаётся стартовым
   (наблюдение и для n=20, и для n=50).

4. **Как разрешить Δε ≥ 0.001?** Что нужно: доработка тангенса, line search
   (уже добавлен), критерии сходимости, или это принципиальное ограничение
   рейт-зависимого n=50?

5. **Сетка.** 232 элемента на зерно — избыточно для текстуры. Нужна ли
   рекомендация по плотности сетки (эл/зерно) для ODF-расчётов?

## 6. Что уже проверено и НЕ является причиной

- **Порядок узлов C3D10.** Была проблема: `mesh.msh` и `mesh.inp` дают разный
  порядок n9/n10 → отрицательные объёмы → падение Flattener. Исправлено
  переходом на `mesh.inp`. Сейчас 0 элементов с отрицательным объёмом.
- **Ссылки секций на наборы.** `*SOLID SECTION, ELSET=polyN` ↔ `*ELSET polyN`
  совпадают. Не причина.
- **Скорость деформации.** Увеличивать нельзя — модель рейт-зависимая, физика
  изменится. Правильный рычаг — размер инкремента.
- **OpenMP/thread-safety.** Не связано; UMAT thread-safe, 0 ошибок.
