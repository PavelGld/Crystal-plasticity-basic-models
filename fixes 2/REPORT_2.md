# CP-UMAT — отчёт, круг 2 (2026-09-03): что осталось и что делать в Abaqus

## 0. Главное

1. **Код после круга 1 корректен.** Присланный `Grain.hpp` побайтно совпадает с моим (текст в
   WORK_SUMMARY п.7 «rotate_stiffness_lab — original T·C·Tᵀ» и п.9.4 «approximate formula is least

2. **Наблюдение «все 64 IP дают одинаковые 9.66 МПа» — не баг.** Мини-МКЭ для
   `tension_8el_same.inp` (один не-identity кватернион на все элементы) даёт при t=0.02 однородные
   **9.21 МПа** на всех элементах. Однородная задача обязана давать однородное поле; ODB, который
   смотрел агент, почти наверняка от `_same`, а не от `_random`. Для random-кейса однородность
   физически невозможна — проверьте по SDV (см. п.3).
3. **Оставшаяся проблема в Abaqus — робастность глобального Ньютона при `n_power = 50`, а не ошибка
   кода.** Доказательство ниже. Лечится настройками `*STEP/*CONTROLS` и/или `n = 20` на этапе
   валидации.

## 1. Что показал мини-МКЭ (тот же код, что в .obj)

FD-проба тангенса *на реальных итератах глобального Ньютона* (переменная `FDPROBE=1` в
`tests/fe_test.cpp`): ошибка `DDSDDE` относительно `d(STRESS)/d(DSTRAN)` — **3e-4 … 2e-3**. Тангенс
согласован. Тем не менее при `n = 50` глобальный Ньютон на некоторых инкрементах расходится: полный
шаг *увеличивает* невязку (0.82 → 1.03 → 0.84 → 1.40 → 2.47 → …). Это подпись негладкого отклика:
при n=50 поверхность текучести кристалла практически многогранная с острыми вершинами, итерата,
перескочившая вершину, попадает в область с другим набором активных систем и другим тангенсом.

Тот же расчёт с `n_power = 20` (`NPOW=20 ./fe_test r 0.05`): расходимостей нет, dt растёт до
максимума, 14 инкрементов до t=0.05, единственный cutback — на первом инкременте (упругий
предиктор при dt=0.005 даёт Δε=5e-4 ≫ упругий предел ~1e-4 при tc0=6 МПа). Сходимость линейная,
×3–10 за итерацию, 5–6 итераций на инкремент — нормально для CPFEM (переключение активных систем
между итератами), но **ровно это ломает дефолтные правила Abaqus**:

- `I_0 = 4`: после 4 итераций Abaqus оценивает скорость сходимости и режет шаг, если «не успеет» за
  `I_C = 16` → при 5–6 итерациях с «плато» на 3–4-й итерации это срабатывает регулярно;
- dt увеличивается только если два инкремента подряд сошлись быстрее `I_A = 5` итераций → при 5–6
  итерациях dt **никогда не растёт** → «0.0634 за 200 инкрементов» = TOO MANY INCREMENTS.

Мини-МКЭ не имеет этих правил, поэтому «проходит»; Abaqus — нет. Разница именно в этом, а не в
порядке вызовов UMAT или инициализации STATEV.

## 2. Что менять в Abaqus (`inp/tension_8el_random_n20.inp` — готовый файл)

```
*STEP, NLGEOM=NO, INC=2000, UNSYMM=YES
*STATIC
0.0005, 1.0, 1e-8, 0.01
*CONTROLS, PARAMETERS=TIME INCREMENTATION
8, 10, 9, 16, 10, 4, 12, 5
*CONTROLS, PARAMETERS=LINE SEARCH
5, 1.0, 0.0001, 0.25, 0.10
...
*ELEMENT OUTPUT
S, SDV
```

- `n_power = 20` в PROPS[9] (второе число второй строки каждого материала) — на этапе валидации.
  При n=50 закон почти rate-independent; возвращать n=50 имеет смысл только после того, как всё
  сходится при 20.
- начальный dt 0.0005 (убирает cutback на первом инкременте), max dt 0.01, INC=2000;
- `I_0 = 8, I_R = 10` — Abaqus перестаёт паниковать на 5–6 итерациях; `UNSYMM=YES` на шаге
  (у вас стоит только на материале — на `*STEP` он тоже нужен для несимметричного солвера);
- line search — прямое лекарство от «полный шаг увеличивает невязку»;
- `SDV` в выводе — чтобы проверить ориентации.

Порядок прогонов: `tension_random.inp` (n=20) → `tension_8el_same.inp` → `tension_8el_random_n20.inp`.
Ожидание для random: сходится, S33 по элементам различаются (в мини-МКЭ при t=0.05 разброс
заметный), число итераций 4–6.

## 3. Как проверить ориентации в Abaqus (30 секунд)

В `cp_umat.cpp` уже пишется `STATEV[60..63] = q(w,x,y,z)`, `STATEV[64] = NOEL`. В Abaqus нумерация
SDV с единицы → это **SDV61–SDV64 и SDV65**. В Viewer/скрипте: для каждого элемента SDV61–64 должны
совпадать с PROPS[10–13] его материала, SDV65 — с номером элемента. Если у всех элементов SDV61–64
одинаковы — тогда (и только тогда) искать проблему на стороне Abaqus/PROPS.

## 4. Изменения кода в этом круге (только `cp_umat/cp_umat.cpp`)

- защита `DTIME <= 0`: Abaqus может дёрнуть UMAT с нулевым инкрементом (начальная жёсткость);
  раньше это давало `L = D/0 = NaN`. Теперь возвращается текущее напряжение и упругая матрица без
  интегрирования.
- `tests/fe_test.cpp`: переменные окружения `FDPROBE=1` (FD-проба тангенса на итератах) и `NPOW=<n>`
  (переопределение n_power).

`Grain.hpp` не менялся — используйте версию из круга 1 (она же у вас в репозитории).

## 5. Если после п.2 всё ещё TOO MANY ATTEMPTS

Тогда нужны данные, а не гипотезы: пришлите `.msg` файл (в нём по итерациям: наибольшая невязка,
узел, где она достигается, и причина cutback'а), `.sta`, и значения SDV61–65 по элементам из ODB.
По `.msg` сразу видно, «плато на 3–4-й итерации» это или локальный провал (`PNEWDT=0.25` от UMAT).

## 6. Что ещё можно улучшить в коде (не блокирует, для следующего круга)

- Точная производная внутреннего fixed-point по упрочнению: сейчас `G` строится по 3 sweep'ам с
  коэффициентами в финальной точке (ошибка ~1e-3). Точный вариант: на сошедшемся γ̇ решить
  `(I − diag(b_i)·H·dt)·G = diag(a_i)·Ms` (24×24, один LU) — тангенс станет точным до 1e-6 и уберёт
  остаток линейности в хвосте.
- Согласованный поворот тангенса: `T(R_end)·C·T(R_startᵀ)` вместо `R_end` с обеих сторон
  (лаг ротации Тейлора внутри инкремента).
- Кламп `RATIO_MAX = 2`: в клампе производная считается как у неклампированной функции; на
  сошедшемся состоянии не влияет, но замедляет локальный Ньютон на «диких» trial-состояниях.
- `static CPUMAT` → per-IP/thread-local перед `cpus > 1`.
